## completed

1. **`scripts/factory/history.mjs`** (NEW) — pure-data history module:
   - `snapshotRows(model, project, ts)` → one row per mission in the
     traceability model, shape `{ts, project, slug, state,
     features:"handoffs/specs", rounds, verdict, reqIds}` (FIXED by
     plan.md). `rounds` = `lastVerdict.round` (0 if null); `verdict` =
     `lastVerdict.verdict` (null if null); `reqIds` = the Requirements
     array from the model (or []).
   - `appendSnapshots(historyPath, rows)` → JSONL append (mkdir -p parent,
     empty/null → no-op). Pure dumb append — the caller decides what to
     append (no dedup at this layer).
   - `readHistory(historyPath)` → tolerant JSONL parse: missing file → [],
     corrupt/partial line silently skipped, never throws. Each valid line
     must parse to an object with `slug` string.
   - `aggregate(rows, {now, missionsDir})` → global + per-project stats:
     `missõesConcluídas` (unique slugs reaching Done, deduped),
     `missõesPorSemana` (Done slugs ÷ max(1, weeks(first→last snapshot))),
     `leadTimeMediano` (median of per-Done-slug lead times in days;
     first snapshot → first Done snapshot), `rondasMédia` (mean of latest
     `rounds` per slug), `tokensTotal` + `atençãoPorFeature` (read from
     each mission's `metrics.jsonl` when `missionsDir` provided; attention
     = touchpoint+intervention+escalation ÷ total handoff count). Also
     `perMission[]` table (slug, estadoAtual, leadTime, rondas,
     últimoVerdict, data). Missing data → null, never crash.

## notes for W5 (integration + backfill + real-repo end-to-end)

- **The Histórico tab is live on the dashboard now.** When you do the
  real-repo end-to-end run (`pnpm ship` or manual autopublish), the
  dashboard at `/wahub/index.html` will show a third tab with real history
  data from `factory/history.jsonl`. The existing 60 rows in that file
  (including pre-hotfix test duplicates) will aggregate cleanly —
  `readHistory` skips corrupt lines, `aggregate` deduplicates by slug
  (latest snapshot wins for state/rounds; unique-slug count for concluded).

- **`stripHistoryPanel` is the key hash-guard addition.** Without it,
  appending history snapshots changes the Histórico tab content → changes
  the hash → triggers another publish → appends more history → infinite
  loop. The panel is wrapped in `<!--hist-start-->…<!--hist-end-->` markers
  (in board-report.mjs) and stripped from the hash (in
  board-autopublish.mjs's `contentHash`). If you add any other
  non-model-derived content to the dashboard HTML, either (a) strip it
  from the hash too, or (b) make it deterministic from the model so it
  doesn't change between identical-state renders.

- **The existing `factory/history.jsonl` has 60 rows** (including
  pre-hotfix duplicates from when test-spawned autopublish was unguarded).
  The orchestrator hotfix (`a1b4dcd`) stopped the bleeding. You may want
  to clean up the duplicates (keep only the last snapshot per slug+state)
  or leave them — `aggregate` handles them gracefully. Do NOT delete the
  file outright: it's the only history we have for `factory-live-board`
  and `sdr-flow-0703`.

- **`board-report.mjs` now reads `factory/history.jsonl` by default.**
  The autopublish funnel spawns board-report without `--history`, so it
  falls back to `<repoRoot>/factory/history.jsonl`. This is correct for
  the published board. If you run board-report standalone with `--repo
  <tmp>`, it reads `<tmp>/factory/history.jsonl` — empty/missing →
  "sem dados ainda" in the Histórico tab.

- **History data is in a separate `<script id="history">` tag**, NOT in
  the `<script id="model">` tag. This is deliberate: the model JSON is
  part of the content hash (stripped only of `generatedAt`), so putting
  history in it would make the hash history-dependent. The separate tag
  is stripped entirely by `stripHistoryPanel` before hashing. If you add
  a fourth embedded JSON payload, follow the same pattern (separate
  `<script>` tag + strip from hash).

- **`aggregate`'s `now` parameter** is accepted for test determinism but
  does NOT affect any rendered value. All computed metrics are derived
  from history.jsonl timestamps and metrics.jsonl content only. This
  satisfies invariant (d): no wall-clock-derived values in the rendered
  Histórico tab.

## unmet_knowledge

- **`stripHistoryPanel` must strip BOTH the visible panel AND the embedded
  JSON.** Initially I considered putting history data inside the existing
  `<script id="model">` tag (the spec says "Data injected via the embedded
  JSON blob like the other tabs"). But the model JSON is part of the
  content hash (only `generatedAt` is stripped), so history data in it
  would make the hash history-dependent → republish loop. The fix: put
  history in a SEPARATE `<script id="history">` tag and strip BOTH the
  visible `<!--hist-start-->…<!--hist-end-->` panel and the separate
  script tag from the hash. The spec's "like the other tabs" means "use
  the same embedded-JSON technique", not "put it in the same tag".

- **The autopublish's `appendHistorySnapshots` extracts the model from the
  rendered HTML** (via `extractModelFromHtml`), NOT by re-reading disk
  (like W2's inline version did). This is cleaner — the model already
  carries everything board-report computed (slug, status, requirements,
  features, handoffs, lastVerdict) — and avoids duplicate disk reads.
  The trade-off: if board-report's embedded model JSON ever changes shape
  (e.g., adds fields, renames keys), `snapshotRows` must be updated to
  match. Today the model shape is stable (board-report.mjs hasn't changed
  its `buildTraceabilityModel` return type since feature 01).

- **`readHistory` validates that each parsed line has a `slug` string
  property.** Lines that parse as JSON but are arrays, primitives, or
  objects without `slug` are silently skipped. This catches edge cases
  where a partial write or a test artifact leaves non-history JSON in the
  file. The real `factory/history.jsonl` is all well-formed rows (verified
  by reading all 60 lines).

- **`aggregate` handles the pre-hotfix duplicate rows** by grouping by
  slug and sorting chronologically. `missõesConcluídas` counts unique
  slugs (not rows), `rondasMédia` uses the latest snapshot's `rounds` per
  slug, and `leadTime` uses the first→first-Done snapshot pair. Duplicate
  rows with the same state don't inflate any metric. But the `data` column
  in the per-mission table shows the LATEST snapshot's ts — if there are
  near-duplicate rows (same slug, same state, ts within milliseconds),
  the latest wins by ts comparison.
