## unmet_knowledge

- **`stripTimestampLines` must strip BOTH `gerado em` AND `"generatedAt"`.** The plan/spec said "the `gerado em` timestamp line stripped", but board-report.mjs embeds the model as `<script type="application/json" id="model">${JSON.stringify({generatedAt, ...}, null, 2)}</script>`. The pretty-printed JSON puts `"generatedAt": "<iso>"` on its OWN line (2-space indent), so it survives a `gerado em`-only filter and makes the hash volatile across identical-state renders. My first GREEN run caught this: two identical-state runs produced different hashes (`1f07984c008d` vs `73740cce0bf7`). Fix: filter lines containing `gerado em` OR `"generatedAt"`. The full model JSON (everything except `generatedAt`) is preserved, so real content changes still move the hash. **If W3/W4 add more volatile fields to the rendered HTML, they must be added to `stripTimestampLines` or the hash guard will thrash.**
- **`board-publish.sh` still targets `/scrumban/`** (the old single-board URL). Plan.md decision `rsync target becomes deploy-host:/opt/app/factory/public/` is W3's repoint. My funnel delegates real-run rsync to board-publish.sh as-is; my `--dry-run` prints the intended (`public/`) target so operators see where the funnel is heading. There's a temporary dry-run/real-run target mismatch in feature 02 that W3 resolves.
- **`board-report.mjs` requires a PRD file** (`if (!existsSync(prdPath)) return 1`). My funnel surfaces that as a render error → soft-fail log + exit 0 (or exit 1 with `--strict`). W3's real `projects.json` must point `prd` at an existing file; the fixture in my test uses a minimal 6-column PRD matching the `parseBacklogTables` HEADER (`| ID | Recurso | Porquê / fonte | Prova | Risco | Situação |`).
- **The autopublish `triggerAutopublish()` in verdict.mjs/ratify.mjs uses `spawn` (async) not `spawnSync`.** This is deliberate: detached + unref so the binding never blocks. But it means the autopublish child is fire-and-forget — the parent verdict/ratify process may exit before autopublish finishes. That's fine for a soft publishing layer, but if W4's history aggregation needs deterministic ordering across rapid verdict→ratify sequences, the detached spawns could race. The hash guard absorbs concurrent double-fire (both compute the same hash, one writes the memo, the other sees "sem mudanças"), so no correctness risk — just a possible double-render in the race window.
- **`factory/.publish.log` appends forever** (one line per run). Nothing rotates it. It's gitignored, so it won't bloat the repo, but a long-running factory could grow it. Not a feature-02 concern; flagging for whoever owns the deploy.
