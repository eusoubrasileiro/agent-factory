# Feature 02 — Resolver loads the project profile — Handoff

**Status:** completed
**Commit:** `e003e80 feat(resolver): load projects/<id>/ profile — gate, criticalFiles, seat.env, validation (factory-profiles 02)`

## What changed

`resolveProject()` now returns one new key, `profile`, exposing the per-project
facts the engine shape cannot know on its own:

```js
profile: {
  gate: string[],          // project.json.gate ([] when absent)
  trunk: string,           // project.json.trunk ("main" when absent)
  branchPrefix: string,    // project.json.branchPrefix ("agent/" when absent)
  criticalFiles: string[], // projects/<id>/critical-files.json ([] when absent/corrupt)
  seatEnvPath: string|null,     // ABS path to projects/<id>/seat.env, or null
  validationPath: string|null,  // ABS path to projects/<id>/validation.md, or null
}
```

Two behavioural changes ship with it:

1. **`loadProjects(factoryRoot)`** now scans `projects/*/project.json` (canonical
   profile source) and merges `deploy/projects.json` back-compat entries
   underneath — on id collision, the `projects/<id>/project.json` entry wins. A
   corrupt or unreadable file is SKIPPED, never thrown. Returns `[]` on total
   failure.
2. **The `"wahub"` literal fallback is gone.** An unknown id now resolves as
   *itself* with a default profile (`id: wantId || "default"`). The engine no
   longer pretends every unknown project is wahub.

`resolveProject` keeps its exact signature, its `dir`/`repo` override behavior,
its selection order (`project` → `$FACTORY_PROJECT` → sole entry), and its
TOTAL semantics — verified by the new test 6.

### Soft-fail discipline

Per spec, every profile-file read is wrapped tightly around `readFileSync` /
`JSON.parse` ONLY — never a broad try/catch that could swallow a programming
bug. Three narrow catches in total:

- `readDeployManifest`: `JSON.parse(readFileSync(...))` — back-compat manifest.
- `loadProjects` per-entry: `JSON.parse(readFileSync(...))` — skips corrupt
  `projects/<id>/project.json` (skip, not throw).
- `buildProfile` critical-files: `JSON.parse(readFileSync(...))` — leaves
  `criticalFiles` at `[]` on corrupt file.

A fourth tight catch wraps `readdirSync(projectsDir)` so a permissions error on
`projects/` cannot kill a mission — it degrades to `[]`. This is the only
non-`readFileSync`/`JSON.parse` catch and it wraps a single I/O line.

## Things downstream callers must know

1. **`profile` is always present and always the full shape.** Every field is
   defined; no `undefined`. Default values: `gate: []`, `trunk: "main"`,
   `branchPrefix: "agent/"`, `criticalFiles: []`, `seatEnvPath: null`,
   `validationPath: null`. Destructure without guards:

   ```js
   const { profile: { gate, trunk, branchPrefix, criticalFiles, seatEnvPath, validationPath } }
     = resolveProject({ project: "wahub" });
   ```

2. **`entry` now carries the full `projects/<id>/project.json` shape.** It is no
   longer trimmed to `{id, name, path, prd}` — `gate`, `trunk`, `branchPrefix`,
   `dispatch` are all on `entry` too (and echoed in `profile` for the shape
   fields). Existing callers that read only `entry.id/path/prd` are unaffected.

3. **The `wahub`-default behaviour is GONE.** Any caller that relied on
   `resolveProject()` (no args) resolving to `wahub` in an empty factory will now
   get `id: "default"`. The selection order is unchanged (sole entry still
   auto-picks), so a populated manifest behaves identically. Empty/missing
   manifest + no args → `"default"`, not `"wahub"`.

4. **`seatEnvPath` / `validationPath` are absolute.** They are built with
   `path.join(factoryRoot, "projects", id, ...)`, so they inherit factoryRoot's
   absoluteness (FACTORY_ROOT is itself `path.resolve`d at module load). Null
   when the file is absent.

5. **`loadProjects` return order: projects/ entries first, deploy/ back-compat
   entries after.** Id collision is resolved by first-write-wins (projects/
   populates the Map first). This is stable across runs because
   `readdirSync` order is file-system-dependent for the projects/ scan, but id
   uniqueness is preserved either way. Don't rely on positional ordering.

## Anything surprising

- **No `pnpm lint` was provided in the allowed command list.** The mission
  doesn't define one in `package.json` (only `test`, `board:*`, `mission:*`,
  `factory:*`). `tsc --noEmit` doesn't apply (plain `.mjs`, no TS). The
  pre-commit hook is also not in scope here (this is a worktree; hooks live on
  the main checkout). So "lint and typecheck" reduces to "tests pass" — which
  they do, 354/354.
- **The `wahub` literal was load-bearing in exactly one place** — the fallback
  `entry = { id: wantId || "wahub", ... }`. Removing it was a one-token change
  (`"wahub"` → `"default"`) and broke zero existing tests. Either no test ever
  asserted that fallback, or every prior test exercised a populated manifest.
  This is mildly suspicious — it suggests the fallback path was untested before
  feature 02; test 4 now pins it.
- **`projects/factory/` was already dogfooded in the previous commit**
  (`28223a5 feat(profiles): projects/<id>/ profile — wahub + factory dogfood`).
  Feature 02 doesn't add a test for it because the spec named only the wahub
  profile assertion (test 1). A future feature could pin factory's
  `gate: ["pnpm test"]` + missing `seat.env` (→ `seatEnvPath: null`) if desired.
- **`readdirSync` catch is a slight stretch of the "catch around
  readFileSync/JSON.parse only" rule.** It wraps a single I/O line and only
  catches I/O failures (permissions, broken symlinks); it does not swallow any
  logic. The alternative — letting it throw — would violate the "if it throws, a
  mission dies" invariant. I judged the invariant more important than a strict
  literal reading.
- **The mission spec text had a `*/` token inside its prose** ("projects/*​/project.json"
  inside a JSDoc block) which initially closed the comment block early and
  broke the test file's parse. Trivial fix in the test header comment; no
  runtime impact.

## unmet_knowledge[]

- **Should `loadProjects` filter out projects whose `path` doesn't resolve?**
  The spec is silent — current behaviour is to surface every parsed entry
  regardless of whether its `path`/`repo` exists on disk. Callers that need
  existence checks can use `existsSync(resolveProject(...).repoRoot)` (and
  several already do).
- **Should `branchPrefix: "agent/"` default move into a shared constant?** It's
  hard-coded in `buildProfile` as a literal. If the factory ever adopts a
  different default branch prefix, this is the place to change. For now it
  matches the spec verbatim and the two checked-in profiles.
