# Feature 03 — The cage renders base template + project profile — Handoff

**Status:** completed
**Commit:** `253035a feat(cage): render per-project Critical Files from the profile (factory-profiles 03)`

## What changed

The cage engine no longer knows any product literally. The 13 wahub-specific
deny rules moved out of `templates/settings-external.json`; the per-project
Edit/Write denies are now generated at render time from the active profile's
`projects/<id>/critical-files.json` (loaded by Feature 02's `resolveProject`).

Three new API surfaces in `scripts/cage-settings.mjs`:

1. **`criticalFileRules(globs = [])`** — pure function. Each glob yields BOTH an
   `Edit` and a `Write` rule, fs-absolute (`//`) anchored via the unsubstituted
   `{{WORKTREE}}` placeholder. Non-array / empty / wrong-shaped input → `[]`,
   never throws. The placeholder is intentionally left intact so the existing
   `renderCageSettings` walk + `auditCageSettings` trap-detector cover them too.

   ```js
   criticalFileRules(["backend/src/bot/**"])
   // → ["Edit(//{{WORKTREE}}/backend/src/bot/**)",
   //    "Write(//{{WORKTREE}}/backend/src/bot/**)"]
   ```

2. **`renderCageSettings(template, worktreeAbs, opts = {})`** — new third
   parameter `{ criticalFiles = [] }`. Appends `criticalFileRules(criticalFiles)`
   to `template.permissions.deny` BEFORE the `{{WORKTREE}}` walk, so the existing
   anchoring logic substitutes them. Two-arg callers keep working unchanged
   (every pre-existing render test passes untouched).

3. **`writeCageSettings(worktreeAbs, opts = {})`** — second arg is now an options
   object `{ templatePath = TEMPLATE_PATH, project, factoryRoot }`. **Back-compat:
   a string second arg is still treated as `templatePath`** (the load-bearing
   `"writeCageSettings: refuses to write a broken cage (fail-closed)"` test
   passes a string path and was not touched). When `project` is given, loads
   `criticalFiles` via `resolveProject({ project }, factoryRoot).profile.criticalFiles`
   — total, no try/catch (per spec).

4. **CLI**: `render|print <worktree> [--project <id>]`. Header Usage block + the
   `_readme` in the template both updated to describe the new model.

The template ships the GENERIC BASE only: the `sandbox` block, the two
`.claude/settings*.json` self-protection rules, the `.env` / `.env.*` /
`~/.config/amiticia/**` / `~/.ssh/**` reads, and all five `Bash(...)` rules.

## Security invariants — held

The three CRITICAL invariants from the mission prompt, each empirically held:

1. **Never emit a single-leading-slash path rule.** `criticalFileRules` always
   emits `//{{WORKTREE}}/<glob>` (double slash). The `auditCageSettings`
   trap-detector is unchanged and still flags any `Edit/Write/Read` rule whose
   target lacks a `//`, `~/`, or `./` prefix. A rule generated from a malformed
   glob would be caught at audit time, and `writeCageSettings` throws before
   any disk write on a non-empty problem list.

2. **Never re-broaden `.claude` deny to `.claude/**`.** The template still ships
   the narrow `Edit(//{{WORKTREE}}/.claude/settings*.json)` +
   `Write(//{{WORKTREE}}/.claude/settings*.json)` pair and nothing broader. The
   regression pin (`the shipped template does NOT deny all of .claude/**`) passes
   unchanged.

3. **A cage failing its own audit never reaches disk.** `writeCageSettings`
   calls `auditCageSettings` BEFORE `writeFileSync` and throws on any problem.
   The new criticalFileRules-generated rules pass through the same audit (they
   are `//`-anchored, so they are clean), but the gate is unchanged.

## Things downstream callers must know

1. **`writeCageSettings` second arg is now overloaded.** A string → treated as
   `templatePath` (back-compat). An object → `{ templatePath?, project?,
   factoryRoot? }`. Existing callers that pass nothing or a string keep working
   identically. New callers pass `{ project: <id> }` to pull Critical Files.

2. **`factoryRoot` is an undocumented-but-useful third option.** The spec named
   only `{ templatePath, project }`, but I added `factoryRoot` for testability:
   it threads straight into `resolveProject({ project }, factoryRoot)`. Without
   it, the engine test for writeCageSettings would have to couple to a real
   checked-in profile (wahub), undoing the engine/product separation this
   feature just established. With it, test 4 builds a synthetic profile in a
   tmpdir and stays engine-pure. The option is additive and defaults to
   `FACTORY_ROOT` via `resolveProject`.

3. **`renderCageSettings` with a `criticalFiles` opt does NOT mutate the input.**
   It shallow-copies `template` and `template.permissions` before appending, so
   callers can reuse the same parsed template across renders with different
   profiles. The deny array is a fresh `[...orig, ...extra]`.

4. **CLI `print` does NOT write to disk and does NOT run the audit.** It only
   renders + substitutes. Use `render` for the audited write path. This matches
   the pre-feature CLI behavior (print was always render-only).

5. **The wahub critical-files coverage moved to Feature 05.** Downstream
   conformance tests should assert that `renderCageSettings(loadTemplate(), WT,
   { criticalFiles: resolveProject({project:"wahub"}).profile.criticalFiles })`
   denies each of the 12 wahub globs as both Edit and Write. This file no longer
   pins that — deliberately.

## Anything surprising

- **The mission prompt's `_readme` rule was "explain that product Critical Files
  now come from the profile"**, not "delete the _readme". I kept the original
  prose block intact and appended a new "PRODUCT CRITICAL FILES (Feature 03)"
  paragraph. The existing `renderCageSettings: strips the _readme prose block`
  test confirms the _readme never reaches the emitted cage, so the prose length
  is free — it's only for the human reading the checked-in template.

- **The initial RED was an import crash, not an assertion failure.** Because the
  new tests import `criticalFileRules` and the symbol didn't exist yet, the
  whole test module failed to instantiate with `SyntaxError: ... does not
  provide an export named 'criticalFileRules'`. This is the cleanest possible
  RED — zero false positives from partially-implemented logic. After adding the
  export, 3 of the 4 tests went green immediately; the 4th (writeCageSettings
  with a synthetic profile) caught a real anchoring bug in my test assertion
  (I'd forgotten that `renderCageSettings` strips the leading `/` from the
  worktree to form the `//`-anchored rule). Fixed the assertion to mirror the
  anchor logic; implementation was correct.

- **`buildSettingsInput` is the natural factoring.** The spec didn't name a
  helper, but both `writeCageSettings` and the CLI's `print` path need to do
  "load template + resolve project critical files". Extracting it avoids
  duplicating the back-compat string-detection + project-resolution logic
  between the two call sites. It's private (not exported) and has a single
  unit-test-irrelevant responsibility.

- **No `pnpm lint` / typecheck applies.** Same as Feature 02: plain `.mjs`, no
  TS, no lint script in `package.json`. "Lint and typecheck" reduces to "tests
  pass" — 359/359.

- **`criticalFileRules` filters non-string array entries silently.** The spec
  says "non-array or empty input returns []" and "never throws". An array with
  a non-string element (e.g. `["a/**", 42, null]`) is technically an array but
  not all strings; I skip the non-strings rather than throw or coerce. This is
  defensive but narrowly so — it protects the "never throws" contract without
  inventing validation errors. The `critical-files.json` format is documented
  as a JSON array of globs, so well-formed profiles never hit this path.

## unmet_knowledge[]

- **Should `criticalFileRules` normalize a glob with a leading slash?** E.g.
  `/backend/**` would today produce `//{{WORKTREE}}//backend/**` (doubled
  separator mid-path). The audit does not flag this (it only checks the rule's
  prefix), and no checked-in `critical-files.json` has such a glob, so the
  question is moot for now. A future hardening could strip a leading `/` from
  each glob, but the spec was explicit about the exact output shape
  (`//{{WORKTREE}}/${g}`), so I preserved it verbatim.
- **Should the CLI `print` path also run `auditCageSettings`?** Today it does
  not — it's render-only for human inspection. The spec's Done-When only asks
  that `print` show the rules, which it does. Running the audit on print would
  be a friendlier UX (catch a bad profile before `render`), but it's out of
  scope here.
