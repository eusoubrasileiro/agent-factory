# Feature 05 — Profile conformance suite (the enforcement) — Handoff

**Status:** completed
**Commit:** `726ac58 test(profiles): per-profile conformance suite + no-product-literals meta (factory-profiles 05)`

## What changed

A single new test file — `scripts/project-profile.test.mjs` (311 lines) — that turns
"the engine is generic" from an aspiration into a load-bearing, fail-loud
invariant. Nothing else was touched.

The suite has two halves plus a guard:

- **Guard** — `projects/ contains at least one profile`. An empty `projects/`
  scan must never masquerade as a green suite; if the discovery loop runs zero
  times, this test fails with a clear message naming the directory it scanned.
- **Part 1** — for every `projects/<id>/` subdir holding a `project.json`, eight
  named tests run. Test names carry the profile id verbatim, so a failure says
  *which* project broke (e.g. `profile wahub: critical-files.json is an array…`).
- **Part 2** — `engine sources carry no product literals`. Scans
  `scripts/*.mjs` (excluding `*.test.mjs`), `scripts/lib/*.mjs`, `templates/*`,
  and `skills/*/SKILL.md` for any non-`factory` profile id, derived live from
  `projects/`. Reports every offender as `file:line (id: …)` so the failure is
  actionable.

The suite is **read-only**: no `mkdtempSync`, no writes, no network. The
"clean up tmp in a `finally`" convention is vacuously satisfied.

### Skips

Both new skips are **spec-mandated**, not workarounds:

- `profile factory: seat.env…` — Part 1 test 6 says "`t.skip()` when the file is
  absent (the `factory` profile has none)". `projects/factory/seat.env` does not
  exist; the skip reason names the path.
- `profile wahub: path resolves to an existing checkout` — Part 1 test 7 says
  "`t.skip()` when the resolved `repoRoot` does not exist, so the suite stays
  green on a machine that has the factory checkout but not every product". In
  this worktree, `FACTORY_ROOT` resolves to
  `…/tools/factory/.worktrees/factory-profiles`, so wahub's
  `path: "../../products/wahub"` resolves to
  `…/tools/factory/products/wahub` — a path that exists only from the **main**
  factory checkout (`…/repositories/products/wahub`), not from a worktree. The
  product checkout is on disk; the resolver's relative anchor just isn't valid
  inside a worktree subdir. The skip is exactly the behaviour the spec asked
  for. (`profile factory: path resolves…` does NOT skip — factory's
  `path: "."` resolves to the worktree itself, which obviously exists.)

## Things downstream callers must know

1. **The forbidden-id list is derived, never hardcoded.** Adding a new
   `projects/<id>/` profile automatically (a) extends Part 1 with 8 new tests
   and (b) extends Part 2's forbidden-id list (unless the new id is `factory`).
   Onboarding a product cannot ship without the conformance suite already
   passing for it.

2. **The Part 2 exemption for `*.test.mjs` is architectural, not a loophole.**
   Engine tests legitimately use real profile ids as opaque fixtures (see
   `project-resolver.test.mjs`, `history.test.mjs`, `board-*.test.mjs`), and
   the profiles themselves are checked into this repo. The rule under test is
   "shipping engine code never names a product"; tests are not shipped engine
   code. The comment at the head of Part 2 states this so a future maintainer
   doesn't tighten the scan by accident.

3. **Part 1 test 7 skips inside worktrees.** `FACTORY_ROOT` is derived from the
   test file's own location, which inside a dispatched worktree is
   `…/.worktrees/<slug>`. Profiles' `path: "../../products/<id>"` is written
   against the **main** factory checkout, so it under-resolves from a worktree.
   This is the spec-mandated skip path: "a machine that has the factory
   checkout but not every product". On the main checkout, the same test runs
   green and verifies the product repo is present.

4. **`/tmp/x` is the spec-named render anchor for Part 1 test 5.** It is never
   written to — `renderCageSettings` is pure. The literal `/tmp/x` appears in
   the asserted rule strings (`Edit(//tmp/x/<glob>)`), matching the engine's
   documented anchor-stripping logic.

5. **The seat.env secret-shape checks use `parseEnv` + `extractSecrets` from
   `scripts/probe-secrets.mjs`.** No new parser was written. The forbidden
   shapes (`eyJ…`, `sk-…`, `AIza…`) are scanned across every parsed value AND
   every `extractSecrets` long-value — belt-and-suspenders, since the spec
   named both helpers and both are exercised.

## Anything surprising

- **Zero on-disk findings.** I expected at least one red — Feature 03's handoff
  hinted at engine-cleanup risk, and the spec's "report any failed profile"
  clause prepared me for one. Both profiles passed clean on the first run. The
  engine-source scan likewise found zero offenders. The architectural work in
  Features 02–04 was thorough; Feature 05 is the pin that holds it.

- **The wahub seat.env contains `JWT_SECRET=<dummy-32-char-test-value>`.**
  This is a *name* that contains the substring `JWT`, not a JWT-shaped *value*
  (no `eyJ…` prefix). The secret-shape regex anchors on the value shape, not
  the key name, so this legitimate dummy passes. The shapes targeted (`eyJ…`,
  `sk-…`, `AIza…`) are unambiguous real-secret prefixes; none of the dummy
  values approach them.

- **`node:test`'s `t.skip()` takes a reason string.** I used
  `t.skip(\`no seat.env at ${seatEnvPath}\`)` and
  `t.skip(\`product checkout not present on this machine: ${repoRoot}\`)` — the
  reason surfaces in the TAP output, so a skipped test is self-documenting
  rather than a silent grey line. The pre-existing
  `board-report.test.mjs:167` uses the older `test.skip.call(this, …)` shape;
  the modern `t.skip()` (the test context method) is cleaner and is what the
  spec named.

- **Part 2 reads every target file with a single `readFileSync` then splits on
  `\n`.** Scanning 17 files this way is sub-millisecond (the whole suite runs
  in ~13s, dominated by the spawn-based verdict/ratify/history tests). A
  stream-based scan would be over-engineering for a few hundred KB of source.

- **The `factory` profile's `path: "."` is the only reason Part 1 test 7 runs
  green inside a worktree at all.** Every product profile that resolves its
  `path` against the main checkout will skip test 7 in a worktree; only the
  self-referential `factory` dogfood profile resolves relative to the engine
  itself, so it always runs. This is a small but real reason the dogfood
  profile is load-bearing for the conformance suite's signal density.

- **No `pnpm lint` / typecheck applies** — same as Features 02 and 03: plain
  `.mjs`, no TS, no lint script in `package.json`. "Lint and typecheck"
  reduces to "tests pass" — 377/377.

## unmet_knowledge[]

- **Should Part 1 test 7 use a stricter "existing checkout" check than
  `existsSync(repoRoot)`?** A directory can exist without being a git checkout
  (e.g. an empty `products/<id>/` placeholder). The spec said "existing
  checkout", and I read that as "path resolves to something on disk" — the
  minimal check that justifies the skip on absent products. A stricter variant
  (`git -C <root> rev-parse`) would couple the suite to git and to the
  product's git state, which felt out of scope. Easy to tighten later if a
  profile ever ships with a half-cloned product.
- **Should Part 2 forbid product ids as whole-words only?** Today it flags any
  substring match (e.g. a hypothetical `wahub` appearing inside a longer
  identifier). With the current single forbidden id this is moot — `wahub` is
  distinctive enough that every hit is real. If a future profile id is a short
  common word (`api`, `web`), the substring scan would false-positive and the
  matcher would need a word-boundary regex. Not added pre-emptively; the spec
  said "contains a product id" and the current shape honours that literally.
- **Should the suite assert the conformance suite file itself is scanned by
  Part 2?** It isn't — Part 2 scans `scripts/*.mjs` excluding `*.test.mjs`, and
  this file is `*.test.mjs`. So the suite exempts itself. This is correct
  (test files are exempt), but a meta-meta test could pin that the exemption
  list includes this very file. Out of scope; the exemption is already
  documented in a comment at the head of Part 2.
