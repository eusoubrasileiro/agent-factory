# Feature 02 — HTML renderer + CLI shell — Handoff

**Status:** completed
**Commit:** `b94f9ff feat(factory): board-report HTML renderer + CLI (factory-dashboard 02)`

## What I built

A pure, self-contained HTML renderer (`renderDashboardHtml`) that consumes the
feature-01 traceability model and produces ONE complete HTML document — all CSS
in a single inline `<style>`, all JS in a single inline `<script>` (vanilla, zero
external URLs, zero CDNs). Plus a thin CLI shell that writes the rendered HTML
to `dist/factory-board/index.html` (mkdir -p the parent).

The renderer is server-side rendered: every requirement row, mission card, lane,
and orphan branch is in the HTML payload. The only client-side JS is (a) tab
switching and (b) in-page anchor jumps from a requirement row to its mission
card (which also switches tabs). Both progressively enhance — with JS disabled,
both tabs are visible in the document flow (the `hidden` attribute is a no-op
without CSS, and the anchor `href="#mission-<slug>"` still works as a fragment
link).

## Renderer contract

```ts
// scripts/factory/board-report.mjs

renderDashboardHtml(model: {
  generatedAt?: string,            // ISO; defaults to new Date().toISOString()
  requirements?: Array<{
    id: string; recurso: string; risco: string; situacao: string;
    missionSlug: string | null; liveStatus: string;
  }>,
  missions?: Array<{
    slug: string; status: string; gateReason: string | null;
    requirements: string[] | null;
    features: number; handoffs: number;
    lastVerdict: { verdict: "PASS" | "FAIL", round: number } | null;
    branch: { name: string; slug: string; merged: boolean; lastCommitISO: string | null } | null;
  }>,
  orphanBranches?: Array<{ name: string; slug: string; merged: boolean; lastCommitISO: string | null }>,
}): string
//  Returns a complete <!doctype html> document. Pure: no disk, no network.
//  - Every interpolated text is HTML-escaped (& < > " ').
//  - The model is embedded as <script type="application/json" id="model">
//    with `<` rewritten to \u003c so a hostile payload can never break out.
//  - Tolerates null/undefined for branch, requirements, lastVerdict, gateReason.
```

### CLI

```bash
node scripts/factory/board-report.mjs \
  [--missions <dir> | --missions-dir <dir>] \
  [--prd <path>] \
  [--repo <root>] \
  [--out <path>]
```

- Defaults: `factory/missions` (relative to the script's repo root),
  `docs/prd/nexus-build-backlog.md`, `dist/factory-board/index.html` (relative
  to CWD). `--missions-dir` is an alias of `--missions` (spec asked for the
  former; feature 01 shipped the latter — both work).
- Exit 0 on success; prints `board-report: N requisitos, M missões -> <out>`.
- Exit 1 if the PRD file does not exist (stderr message, no file written).
- Exit 2 on unknown positional args (usage to stderr).
- `mkdir -p` the parent of `--out` before writing.

### Layout

- **Header**: `Fábrica Nexus — rastreabilidade` + tab bar (Requisitos default,
  Missões).
- **Tab "Requisitos"**: one `<table>` per body A–D ("Corpo A — Inbox",
  "Corpo B — Dashboard/CRM", "Corpo C — SDR/Bot", "Corpo D — Mineração").
  Bodies with zero rows are omitted. Columns: ID · Recurso · Risco (badge,
  classified low/med/high/neutral from the raw cell text) · Status vivo (colored
  badge from `liveStatus`) · Missão (in-page anchor to the mission card, or
  muted "sem missão").
- **Tab "Missões"**: lanes in fixed order `Needs Human · Building · Validating ·
  Planning · Intake · Done · Blocked`. Empty lanes are omitted entirely (no
  header rendered). Each card is a `<details id="mission-<slug>">`:
  - **Summary (always visible)**: slug, `gateReason` badge (amber, when set),
    `handoffs/features` progress (e.g. `2/4`), branch line
    (`agent/<slug> · mergeado|não mergeado · DD/MM`), requirement chips.
  - **Drilldown (click to toggle)**: `N features, M com handoff` line +
    `Último veredicto: PASS|FAIL (rodada N)` when `lastVerdict` is set.
- **Orphan branches**: a `branches sem missão` section at the bottom of the
  Missões tab, only when `orphanBranches` is non-empty. Each branch: name,
  merged state, DD/MM date.
- **Footer**: `gerado em <time datetime="...">...</time> · board-report`.
- **Model embed**: `<script type="application/json" id="model">{...}</script>`
  for debugging — the HTML is fully rendered server-side and does NOT depend on
  this script for display.

### Status color map (CSS classes)

| Status        | Class           | Background | Foreground |
|---------------|-----------------|------------|------------|
| Done          | `done`          | green      | dark green |
| Needs Human   | `needs-human`   | amber      | dark amber |
| Building      | `building`      | blue       | dark blue  |
| Validating    | `validating`    | blue       | dark blue  |
| Planning      | `planning`      | slate      | slate      |
| Intake        | `intake`        | gray       | gray       |
| Blocked       | `blocked`       | red        | dark red   |

Risk badges: `risk-low` (cyan), `risk-med` (amber), `risk-high` (red),
`risk-neutral` (gray) — classified by scanning the raw cell text for
`low`/`med`/`high` (case-insensitive).

  the target is in a hidden tab-panel, so the browser won't scroll to it. This
  matches the spec's "works with JS disabled except tab switching/drill-down".

## Things worker 03 (publish/deploy) must know

1. **The renderer is the public surface.** Import and call directly:
   ```js
   import { renderDashboardHtml, buildTraceabilityModel, collectGitInfo }
     from "./scripts/factory/board-report.mjs";
   const model = buildTraceabilityModel({
     missionsDir, prdPath, gitInfo: collectGitInfo(repoRoot),
   });
   const html = renderDashboardHtml(model);
   ```
   No side effects from the renderer — it's a pure `model → string`. The only
   effects (git reads, file reads, file writes) live in `collectGitInfo`,
   `buildTraceabilityModel`, and the CLI `main()`.

2. **The CLI writes to `dist/factory-board/index.html` by default.** `dist/` is
   now gitignored (top-level). If you wire this into a `pnpm` script or a build
   step, the default path works from the repo root. Override with `--out` for a
   custom location.

3. **Package.json is yours to touch.** Feature 02 explicitly did NOT add a
   `pnpm` script for the board (the spec said "feature 03 owns it"). Suggested
   script name: `"board": "node scripts/factory/board-report.mjs"` (matches the
   existing `"board:sync"` pattern). The summary line format is stable:
   `board-report: N requisitos, M missões -> <out>`.

4. **The HTML is self-contained — no assets to ship alongside.** One file, zero
   external URLs, zero CDN dependencies. You can serve it from any static host,
   open it via `file://`, or inline it into an email. System font stack only.

5. **The model embed (`<script type="application/json" id="model">`) is for
   debugging only.** The HTML does not read it at runtime — everything is
   pre-rendered. If you want a client-side refresh hook later, the embedded
   model is your starting point (parse it, re-render client-side). For now it's
   inert.

6. **Status color mapping is in `STATUS_CLASS` (top of the renderer section).**
   If you add a new mission status, add it there + a corresponding
   `.badge-status.<class>` CSS rule. Unknown statuses fall back to `intake`
   styling (gray).

7. **Body titles are hard-coded in `BODIES`** (A=Inbox, B=Dashboard/CRM,
   C=SDR/Bot, D=Mineração). If the PRD body headers change, update `BODIES` to
   match — the renderer does NOT parse body titles from the PRD (it groups by
   the first letter of the requirement ID).

8. **Lane order is hard-coded in `LANE_ORDER`.** The spec mandates:
   `Needs Human · Building · Validating · Planning · Intake · Done · Blocked`.
   Empty lanes are omitted. Don't reorder without checking the spec.
