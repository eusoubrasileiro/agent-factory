## What I built (the v2 redesign)

v1 whitelisted the intake `summary` field and passed a fixture leak test, but
against the REAL client intake it leaked everything — the summary IS engineering
prose (file:line refs, commit hashes, model names, engagement strategy). A
whitelist that includes `summary` leaks by construction.

v2 is **whitelist by construction in the strict sense** — the page starts from
nothing and adds only a separately-curated label:

- The only client-facing text is `label` from a curated `client-labels.json` map
  (`{ "IN-44": { label, client_visible } }`), authored and ratified apart from
  the intake. The intake `id`/`summary`/`type`/`detail` are NEVER copied into the
  output — `id` is a join key only, `status` drives the PT status word, `date`
  drives the ship date.
- A row renders only if it has a curated, `client_visible: true`, non-empty label
  **AND** that label survives a final fail-closed `isClientSafe()` guard. A bad
  label fails CLOSED — the row vanishes, never leaks.

Two layers of fail-closed defense:
1. **By construction** (`buildClientRows`): only `client_visible:true` + non-empty
   label + guard-passing rows are emitted.
2. **At publish** (`board-autopublish.mjs`): the page is rendered/written ONLY
   when a project declares `intake[]` AND a parseable `client-labels.json` sits
   beside it. No labels ⇒ no `cliente/` dir ⇒ an unlabeled (therefore unsafe)
   page can never be published.

## Module contract

```js
// scripts/client-view.mjs — pure (model in, HTML out; no disk/network/<script>)

mapClientStatus(status): "na fila" | "em construção" | "no ar"
  // New|Distilled|unknown|empty → "na fila"; Ratified → "em construção"; Landed → "no ar"

isClientSafe(text): boolean
  // false if text matches ANY forbidden class (R$, $+digit, tok, model names
  // glm|claude|opus|sonnet|gpt|gemini, detalhamento, pagamento, engagement,
  // gate:, agent/, .ts/.tsx/.mjs, :digits, 7+hex commit, Needs Human, verdict,
  // PASS, FAIL). Curated labels never trip it; it exists so a bad one fails closed.

buildClientRows(intake, labels, missions?): Array<{ label, clientStatus, shippedDate }>
  // one row per intake id that is client_visible:true + non-empty label + safe.
  // EXACTLY those 3 fields, built field-by-field. shippedDate = DD/MM/YYYY only
  // for "no ar" rows (the row's own date — the only landed date in its data);
  // "" otherwise. Never guesses.

renderClientPage({ intake, labels, missions?, generatedAt? }): string
  // self-contained <!doctype html>, lang pt-BR, no <script>, no external URLs.
  // Sections: "O que estamos construindo" (funnel: label · situação · entregue em)
  // and "Novidades da semana" (labels that reached "no ar" within 7d of generatedAt).
  // Footer: `atualizado em <time datetime="…">DD/MM/YYYY HH:MM</time>`.
  // Local esc()/formatDateTime() — no board-report import (contract D).
```

`missions` is accepted for signature fidelity and reserved for a richer per-
requirement landed date; the ship date is derivable from the intake row alone, so
the leak-safe core never depends on it (documented in the JSDoc).

## The leak test is the heart — and it cannot false-pass

`client-view.test.mjs` defines the forbidden classes **independently** of the
implementation (not imported from it), and that list is **byte-for-byte identical**
to `FORBIDDEN_CLASSES` in the guard. Consequences:

- If a label passes `isClientSafe`, it provably passes the leak scan — the test
  can never green-light a leaking label.
- If the guard is disabled, the B1 mutation gate goes red (a label
  `"ver webhook.ts:12"` would render).
- **C1** reads the REAL `clients/tenant-a/requirements-intake.md` (via `parseIntake`)
  + the REAL `client-labels.json`, renders the full page, strips the engine
  footer (whose `HH:MM` legitimately contains `:digits`), and asserts NONE of the
  forbidden classes reaches the HTML. It **skips with a clear message** when the
  real files are absent at test time — it never fake-passes. (In this caged
  sandbox the test runner cannot reach the external `clients/` path, so C1/C2
  skip here; in the real factory checkout — where the validator runs — they
  execute against the genuine data. The synthetic leak fixtures prove the logic
  regardless.)

## How the labels file is found (product-agnostic)

The renderer never names Tenant A. The autopublish wiring resolves
`client-labels.json` as the **sibling of a profile-declared `intake[]` source**:
for each project, `resolveProject(...).profile.intake` gives absolute intake
paths, and the labels file is `path.join(dirname(intakeFile), "client-labels.json")`.
For the live profile that is `clients/tenant-a/client-labels.json`; for any other
client it follows the same rule with no engine change.

## Manual verification performed (since the gate could not self-run)

Every assertion in both test files was traced against the implementation by hand:

- **isClientSafe**: all 16 reject inputs trip a class; all 7 accept inputs trip
  none (incl. confirming no 7-hex run or `:\d` in clean PT labels).
- **mapClientStatus**: every input maps to one of the three words.
- **buildClientRows**: shape is exactly `{label,clientStatus,shippedDate}`;
  hidden/orphan/empty-label/guard-tripping rows are omitted; intake
  id/summary/type/detail never appear in the JSON.
- **renderClientPage**: the rendered body (CSS included — every CSS declaration
  uses `: ` so `:\d` never matches; every color hex is exactly 6 chars so the
  7-hex rule never trips) carries no forbidden class after the footer is stripped.
  Footer matches `atualizado em <time…>DD/MM/YYYY HH:MM</time>`. Novidades window
  correctly excludes a 13-day-old `no ar` row and includes a 2-day-old one.
- **Autopublish E2**: labels-present fixture writes the page and the leaky gist
  never reaches it; labels-absent writes no dir; two runs hash identically.
- **Meta-test**: `grep`-confirmed no `wahub`/`tenant-c` literals in the shipping
  scripts.

## unmet_knowledge[]

- **`shippedDate` source.** The intake row carries a single date (the day it was
  logged) and no separate ship date, so v2 uses that as the only "Landed date
  within the row's data" (contract A3). If a richer per-requirement landed date is
  wanted (e.g. the board mission's merge date via the backlog chain), `missions`
  is already in the signature to carry it — wire `buildClientRows`/`enrichRows`
  to prefer it and fall back to the row date. Ratify before relying on the date
  as a true "delivered-on".
- **Stale `cliente/` cleanup.** The publish gate writes `cliente/` only when
  labels exist; it does not REMOVE a previously-written page if labels later
  vanish (rsync `--delete` would still serve the stale one). Low risk today
  (labels won't typically vanish); flag if the labels file becomes volatile.
- **C1/C2 real-data reachability in CI.** Confirm the CI/validator checkout has
  `clients/tenant-a/` readable so C1/C2 run against the genuine data rather than
  skipping. The skip is safe (never fake-passes) but the real run is the point.
